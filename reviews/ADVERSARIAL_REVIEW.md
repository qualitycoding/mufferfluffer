## Findings

| id | severity | file and line | description and failure scenario | suggested resolution |
|---|---|---|---|---|
| ADV-01 | Medium | vst3/src/processor.cpp:120-127 (`prepareToPlay`), 186-198 (`setStateInformation`); contract at vst3/include/muff/vst3_shell.hpp:18 | **`getTailLengthSeconds()` is stale after a state load until the first `processBlock`.** Parameter values reach the `muff::Effect` only at the top of `processBlock`. `prepareToPlay` stores `hostTailSeconds(effect.tailSeconds())` from the parameters of the previous block, or the defaults. When a host opens a project, the usual order is `setStateInformation`, then activation (`prepareToPlay`), then a read of the tail. At that point the host is given the default-parameter tail. Measured (row 12): Delay with Feedback at 97 % reports **8.24 s** where the correct value is **infinite** (self-oscillating). Lowpass reports 0.21 s against infinite, Chorus 0.15 s against infinite, and Phaser 0.11 s against 0.61 s. JUCE 9.0.5's VST3 wrapper has no way to tell the host that the tail changed: the only restart flag it raises is `kLatencyChanged`, and `getTailSamples` is answered from the current value. So a host that reads the tail at activation keeps the wrong value. In an offline bounce of a project that ends in a Delay at high feedback, such a host stops processing about 8 s after the input ends and cuts the echoes. The same happens to any parameter change made while the transport is stopped. Workaround: extend the render range by hand, or play one block before rendering. That is why this is Medium and not High. The frozen contract is met to the letter ("effect.tailSeconds()"), but the host sees a wrong value. | In `prepareToPlay`, copy every parameter's current value into the effect (the same `fx.setParam(k, currentValue(k))` loop as `processBlock`) before reading `tailSeconds()`. `prepareToPlay` and `processBlock` never run at the same time, so this is allowed. Optionally, in `setStateInformation`, recompute the tail from a second, message-thread-only `muff::Effect` used only for `tailSeconds()`, and call `updateHostDisplay()`. Add a frozen test through HANDOFF.md 9.4: after `setStateInformation` + `prepareToPlay`, and before any block, `getTailLengthSeconds()` equals the value after one block. |
| ADV-02 | Low | vst3/src/processor.cpp:30-40 (`parseStateValue`) | **The "strict" state-value parser accepts malformed numerals.** Its comment says "a plain decimal or scientific number, nothing else". The character whitelist (`0123456789+-.eE` with at least one digit) still lets through `e5`, `--5`, `+-3` (applied as **0**), `1e` (applied as 1) and `1.2.3` (applied as 1.2). `juce::String::getDoubleValue` then parses a prefix silently. Scenario: a state that was corrupted or edited by hand sets Feedback to 0, with no sign anything went wrong, where the contract's intent is to leave such a value alone. JUCE itself never writes such strings, so ordinary save/restore is not affected. | Validate the whole token against `[+-]?(\d+\.?\d*\|\.\d+)([eE][+-]?\d+)?` before converting, or check that the parse consumed every character. Keep the conversion locale-independent: do not use plain `strtod`. Add the five strings to the VST3 state test through 9.4, or record an R- entry. |
| ADV-03 | Low | vst3/src/processor.cpp:186-191; contract vst3/include/muff/vst3_shell.hpp:25 | **A state cut inside its closing root tag is accepted.** The contract says that a truncated blob "leaves every parameter unchanged". JUCE's parser accepts a document whose final `</muff-…>` is incomplete, so 11 to 16 truncation lengths per effect apply the state (row 4e). Every `<param>` is complete in those cases, so the applied values are exactly the saved ones. There is no partial or wrong application, and the only effect is that the contract's wording is not met. Cuts anywhere else are rejected. | Either amend the contract wording ("a truncation that loses only the closing tag is accepted, since every value is present"), or require the decoded text (after removing the trailing NUL) to end with `</muff-<slug>>` before parsing. |

### Notes (no finding)

- **Delay `reset()` at 768 kHz** clears a 7.8 MB line in 0.30 ms. `EffectBase::process` calls `reset()` after a non-finite result (effect_base.cpp, the T-007 path). At 768 kHz with 64-sample blocks (83 µs per block), that recovery would overrun one buffer. None of the attacks above (NaN, ±1e30, a parameter storm, 24 h) ever reached that path, so this note is for information only.
- **Confirmed earlier findings:** the edge-rate probe in rows 7 and 8 shows that taps and tempo are exact at sample resolution in the core, so B2-01 (tap quantised to the host block) is a matter for the shell only. A block size of 8192 makes it worse, as B2-01 states.
- I did not run the project's own test suite (ctest, muff_vst3_tests), and I could not check CI from this sandbox. The step's "suite green" and "CI green" conditions remain for the implementer.
- Each finding should become a frozen test through HANDOFF.md 9.4, or an R- entry, as the step requires. I made no change to the product.
